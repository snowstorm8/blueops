### DR-ANY-CHG-001 - New findings appeared together after a clean assessment

The previous snapshot was complete and had no finding of medium severity or higher; this one has new medium-or-higher findings in at least two different areas.

| | |
|---|---|
| Version | 1.0.0 (pack `changes`) |
| Platforms | any |
| Category | change |
| Nature | correlated |
| Severity | medium: A sudden cluster of independent problems on a previously clean host deserves a look, but a patch or deployment can cause the same picture. |
| Confidence | medium: The previous snapshot was complete, so absence there is trustworthy; the cause of the change is unknown. |
| Enabled by default | yes |
| Needs coverage | `comparison`, `history:1` |

**Why it matters.** Independent new problems that appear together after a clean baseline usually share a cause: a deployment, a package change, or an intrusion.

**Conditions.**

- `clean` on `snapshot`: The previous snapshot was complete and clean \(no medium\+ findings\)  
  `(previous.clean eq True)`
- `fresh` on `new_findings` (at least 2 distinct `category` values): New medium-or-higher findings in at least two categories  
  `severity_rank gte 2`
- `critical_new` on `new_findings` (optional): A new critical finding  
  `severity eq 'critical'`

Requires: `(clean all fresh)`.
Severity becomes **high** when `critical_new`: At least one of the new findings is critical.

**Possible benign causes.**

- Operating system or application upgrades, new deployments, a first run with additional modules enabled.

**Would raise confidence.**

- Package manager and deployment logs between the two snapshots.
- Whether the new findings share paths or accounts.

**Investigate.**

1. List the new findings and look for a common path, account or time.
2. Check change records and package logs between the snapshots.
3. Compare module coverage of the two assessments.

**Remediation.** Triage the new findings by severity; if the cause was an approved change, accept it into the baseline.

**References.**

- NIST SP 800-53 Rev. 5: CM-3, SI-4

**Examples (executed by `rules test`).**

- `match`: two new findings after clean
- `no_match`: new finding in one area only
- `no_match`: previous was not clean
- `indeterminate`: previous coverage incomplete
- `indeterminate`: no earlier snapshot

### DR-ANY-CHG-002 - A previously resolved finding has returned

A medium-or-higher finding that earlier snapshots recorded as resolved is present again.

| | |
|---|---|
| Version | 1.0.0 (pack `changes`) |
| Platforms | any |
| Category | change |
| Nature | indicator |
| Severity | medium: A fix that did not hold means a process re-applied the weakness: configuration management drift, a restored backup, or someone re-introducing it. |
| Confidence | medium: The finding id is stable across snapshots and absence in the earlier snapshot was confirmed by a clean module run. |
| Enabled by default | yes |
| Needs coverage | `history:2` |

**Why it matters.** Re-appearing findings point to something undoing remediation. That is more interesting than a persistent finding because it implies an active cause.

**Conditions.**

- `back` on `findings`: A medium\+ finding that reappeared after being absent  
  `(history.reappeared is_true) all (severity_rank gte 2)`

Requires: `back`. Items are grouped by `id`.

**Possible benign causes.**

- Rollback of an environment to an earlier image; a flapping check at the edge of a threshold.

**Investigate.**

1. Find what changed between the snapshots that included the fix and the re-appearance.
2. Check configuration management and backup restores.
3. Check whether the evidence is the same as before the fix.

**Remediation.** Fix the root cause that re-introduced it \(configuration management, image, backup\), then re-assess.

**References.**

- NIST SP 800-53 Rev. 5: CM-3, CM-6

**Examples (executed by `rules test`).**

- `match`: finding present, absent, present again
- `no_match`: continuously present
- `no_match`: absence was not confirmed \(module failed\)
- `indeterminate`: only one earlier snapshot

### DR-ANY-CHG-004 - Security-relevant configuration changed after a long stable period

A configuration record \(sshd, sudoers, PAM, firewall, security policy, sysctl, event log, ...\) changed after holding the same value in at least three earlier snapshots.

| | |
|---|---|
| Version | 1.0.0 (pack `changes`) |
| Platforms | any |
| Category | change |
| Nature | indicator |
| Severity | medium: A value that was stable for several assessments and then changed is more likely a deliberate act than routine churn. |
| Confidence | medium: The stability history is exact; the cause of the change is not. |
| Enabled by default | yes |
| Needs coverage | `comparison`, `history:3` |

**Why it matters.** Baselines are most valuable for settings that rarely change. A change to one of those is a better lead than a change to a volatile value.

**Conditions.**

- `cfg` on `config_changes`: A security-relevant config record changed after \>= 3 stable snapshots  
  `(domain eq 'config') all (change eq 'modified') all (scope in ['sshd', 'sudoers', 'pam', 'firewall', 'security', 'sysctl', ...]) all (history.before_stable_snapshots gte 3)`

Requires: `cfg`. Items are grouped by `key`.

**Possible benign causes.**

- Scheduled hardening or patch windows.

**Investigate.**

1. Read the before and after values \(detail of the contributing change\).
2. Check change records for the date between the two snapshots.
3. Check who could have edited the file or registry key.

**Remediation.** Revert unapproved changes and investigate how the edit was made; record approved changes in the baseline.

**References.**

- NIST SP 800-53 Rev. 5: CM-3, CM-6

**Examples (executed by `rules test`).**

- `match`: sshd setting changed after 3 stable snapshots
- `indeterminate`: changed after only two stable snapshots
- `no_match`: flapping value is not stable
- `no_match`: unchanged
- `no_match`: change outside the sensitive scopes

### DR-ANY-CHG-005 - Audit coverage decreased since the previous snapshot

One or more modules that finished cleanly in the previous snapshot did not finish cleanly \(or were not run\) in this one.

| | |
|---|---|
| Version | 1.0.0 (pack `changes`) |
| Platforms | any |
| Category | change |
| Nature | observation |
| Severity | low: Lost coverage is not a threat by itself; it means conclusions about the affected areas cannot be drawn this time. |
| Confidence | high: Module statuses are recorded by the engine for both snapshots. |
| Enabled by default | yes |
| Needs coverage | `comparison:exists` |

**Why it matters.** Resolved or missing findings in an area that was not audited are not good news. Collectors can fail because of tampering, resource exhaustion or permission changes, which is itself worth knowing.

**Conditions.**

- `cov` on `snapshot`: Modules degraded or removed compared with the previous snapshot  
  `(coverage.modules_degraded gte 1) any (coverage.modules_removed gte 1)`

Requires: `cov`.

**Possible benign causes.**

- A profile with fewer modules was chosen deliberately.

**Investigate.**

1. Open the module list of the assessment and read the reason of each non-ok module.
2. Check the privileges and tool availability of the run.
3. Re-run the missing modules.

**Remediation.** Re-run the assessment with the same profile and privileges as before; investigate modules that fail repeatedly.

**References.**

- NIST SP 800-53 Rev. 5: AU-6, SI-4

**Examples (executed by `rules test`).**

- `match`: a module timed out
- `match`: a module was dropped
- `no_match`: same coverage
- `no_match`: coverage improved

### DR-ANY-COR-001 - Persistence entry executes a file that the filesystem checks also flagged

A service, task, autorun, cron job or unit refers to a path that a filesystem finding \(world-writable, temporary, unsigned, hidden or recently modified executable\) also lists.

| | |
|---|---|
| Version | 1.0.0 (pack `correlation`) |
| Platforms | any |
| Category | persistence |
| Nature | correlated |
| Severity | high: A startup mechanism that points at a file sitting in an unsafe place or flagged as unusual is the shape of a planted foothold. |
| Confidence | medium: Linking is by a shared path string in two independent findings; the path is exact but the file's purpose is still unknown. |
| Enabled by default | yes |
| Needs coverage | `module:persistence` |

**Why it matters.** Two independent collectors \(startup configuration and file inspection\) describe the same path. That agreement is stronger than either finding alone and shows where to look first.

**Conditions.**

- `start` on `findings`: A suspicious service, task, autorun or cron/unit finding  
  `check_id in ['PER-CRON-002', 'PER-SYSTEMD-001', 'PER-STARTUP-001', 'PER-SHELL-001', 'SVC-PATH-001', 'SVC-UNQUOTED-001', ...]`
- `file` on `findings`: A filesystem finding about an unusual executable or writable file  
  `check_id in ['FS-PERM-003', 'FS-PERM-001', 'FS-PERM-002', 'FS-SUID-002', 'FS-HIDDEN-001', 'FS-EXE-001', ...]`

Requires: `(start all file)`. Items are grouped by `evidence.paths`.

**Possible benign causes.**

- Software legitimately installed under ProgramData or /opt that is also unsigned or recently updated.

**Would raise confidence.**

- Hash and signature of the file; creation time relative to the startup entry.
- Network connections made by the process started from this path.

**Investigate.**

1. Open the shared path: owner, hash, signature, timestamps.
2. Read the startup entry that references it.
3. Check whether other entries reference the same path.

**Remediation.** Preserve the file and the entry as evidence, disable the startup entry, then remove or restore the file from a trusted source.

**References.**

- ATT&CK [T1543](https://attack.mitre.org/techniques/T1543/) (possible): Service/unit persistence can launch attacker-placed files; here the link is only a shared path.
- ATT&CK [T1053](https://attack.mitre.org/techniques/T1053/) (possible): Scheduled execution can launch attacker-placed files; here the link is only a shared path.
- NIST SP 800-53 Rev. 5: SI-7, CM-7

**Examples (executed by `rules test`).**

- `match`: unit executes file in /tmp that is also flagged
- `no_match`: different paths
- `no_match`: persistence finding without a filesystem finding
- `match`: windows service and unsigned exe
- `match`: case differences in paths still join

### DR-ANY-COR-002 - Firewall configuration changed and a new non-loopback listener appeared

Between two snapshots the host firewall configuration changed and a new listener on a non-loopback address appeared.

| | |
|---|---|
| Version | 1.0.0 (pack `correlation`) |
| Platforms | any |
| Category | network-exposure |
| Nature | correlated |
| Severity | medium: Either change can be routine administration; the combination warrants review, not alarm. |
| Confidence | medium: Both changes are exact; the ordering and the relationship between them are not known from two point-in-time snapshots. |
| Enabled by default | yes |
| Needs coverage | `comparison` |

**Why it matters.** Opening a firewall path and starting a listener are two halves of exposing a service. Seeing both since the last snapshot is worth confirming against change records.

**Conditions.**

- `fw` on `config_changes`: A firewall configuration record changed  
  `(domain eq 'config') all (scope eq 'firewall') all (change in ['added', 'modified', 'removed'])`
- `lst` on `config_changes`: A new non-loopback listener  
  `(domain eq 'listeners') all (change eq 'added') all (not ((attrs.bind regex '^127\\.') any (attrs.bind in ['127.0.0.1', '::1', 'localhost', '[::1]'])))`

Requires: `(fw all lst)`.

**Possible benign causes.**

- Planned deployment of a new service with its firewall rule.

**Would raise confidence.**

- Change tickets for the new service.
- The process name and package of the new listener.

**Investigate.**

1. Compare the firewall record's before/after attributes.
2. Identify the process and package behind the new listener.
3. Confirm both against change records.

**Remediation.** Revert the firewall change and stop the service if unplanned; otherwise record the change and update the baseline.

**References.**

- ATT&CK [T1562.004](https://attack.mitre.org/techniques/T1562/004/) (possible): Modifying the host firewall is a defence-evasion technique; the change here may be legitimate.
- NIST SP 800-53 Rev. 5: CM-3, SC-7

**Examples (executed by `rules test`).**

- `match`: firewall changed and listener added
- `no_match`: listener only
- `no_match`: loopback listener
- `indeterminate`: no earlier snapshot

### DR-ANY-COR-003 - Scheduled-job change together with an account or group change

Since the previous snapshot a scheduled job \(cron entry or non-Microsoft task\) was added or modified and a user or group record was also added or modified.

| | |
|---|---|
| Version | 1.0.0 (pack `correlation`) |
| Platforms | any |
| Category | persistence |
| Nature | correlated |
| Severity | medium: New scheduled execution plus a new or changed account is a common attacker sequence, but also routine onboarding; severity is not raised further. |
| Confidence | low: Two point-in-time changes with no proof they are related; the rule excludes built-in Microsoft task churn to reduce noise. |
| Enabled by default | yes |
| Needs coverage | `comparison` |

**Why it matters.** Persistence and access are often established together: a new account to log in with and a scheduled job to keep code running. Neither alone is notable; together they merit a look.

**Conditions.**

- `job` on `config_changes`: A scheduled job added or modified \(not a built-in Windows task\)  
  `(domain eq 'scheduled_tasks') all (change in ['added', 'modified']) all (not (key regex '(?i)^task:\\\\microsoft\\\\windows\\\\'))`
- `acct` on `config_changes`: A user added or modified, or group membership changed  
  `((domain eq 'users') all (change in ['added', 'modified'])) any ((domain eq 'groups') all (change eq 'modified'))`

Requires: `(job all acct)`.

**Possible benign causes.**

- Provisioning or configuration-management runs that create a service account and its job.

**Would raise confidence.**

- The account owning or referenced by the job.
- A recorded change request covering both.

**Investigate.**

1. Read the job's command and schedule; check the account named in it.
2. Compare the account's attributes before and after.
3. Check authentication logs for the new or changed account.

**Remediation.** If unplanned, disable the job and the account after preserving evidence; otherwise update the baseline.

**References.**

- ATT&CK [T1053](https://attack.mitre.org/techniques/T1053/) (possible): Scheduled execution is a persistence technique; the job here may be benign.
- ATT&CK [T1136](https://attack.mitre.org/techniques/T1136/) (possible): Account creation is a persistence technique; the account here may be benign.
- NIST SP 800-53 Rev. 5: CM-3, AC-2

**Examples (executed by `rules test`).**

- `match`: cron job and new user
- `no_match`: job only
- `no_match`: built-in windows task churn
- `indeterminate`: no earlier snapshot

### DR-ANY-COR-004 - Multiple authentication-configuration weaknesses

Three or more different authentication-related weaknesses \(PAM, sshd, password policy, lockout, RDP\) are present on one host.

| | |
|---|---|
| Version | 1.0.0 (pack `correlation`) |
| Platforms | any |
| Category | authentication |
| Nature | correlated |
| Severity | medium: Each weakness is individually low or medium; together they leave credential guessing unthrottled and unchecked. Severity is deliberately not raised for the count. |
| Confidence | medium: The findings are accurate individually; the rule only counts distinct weaknesses. |
| Enabled by default | yes |
| Needs coverage | none |

**Why it matters.** Password guessing and credential reuse succeed where policy, lockout and hashing are all weak. The grouping shows a systemic gap rather than one oversight.

**Conditions.**

- `weak` on `findings` (at least 3 distinct `check_id` values): Authentication findings \(at least 3 different checks\)  
  `check_id in ['ATH-DEFS-001', 'ATH-PWQ-001', 'ATH-LOCKOUT-001', 'ATH-AGING-001', 'PAM-HASH-001', 'PAM-NULLOK-001', ...]`

Requires: `weak`.

**Possible benign causes.**

- Hosts using centralised authentication \(LDAP/SSSD/AD\) where local policy is intentionally minimal.

**Would raise confidence.**

- Failed-logon volume in authentication logs.
- Confirmation that no central policy compensates.

**Investigate.**

1. List the distinct findings and decide which gap to close first \(bypass-class first\).
2. Check authentication logs for guessing patterns.
3. Confirm whether central authentication policy applies.

**Remediation.** Enforce a password-quality module, account lockout, strong hashing and secure sshd/RDP settings; coordinate with scored-service account owners first.

**References.**

- ATT&CK [T1110](https://attack.mitre.org/techniques/T1110/) (possible): Weak lockout and password policy facilitate brute-force attacks; none is observed.
- NIST SP 800-53 Rev. 5: IA-5, AC-7

**Examples (executed by `rules test`).**

- `match`: three authentication findings
- `no_match`: two findings
- `match`: count does not raise severity
- `match`: windows policy findings

### DR-ANY-COR-005 - Logging or protection impaired alongside a persistence indicator

A log-impairment or protection-disabling finding appears on the same host as a high-signal persistence finding.

| | |
|---|---|
| Version | 1.0.0 (pack `correlation`) |
| Platforms | any |
| Category | defense-evasion |
| Nature | correlated |
| Severity | high: Persistence indicators are concerning on their own; paired with reduced logging or protection they suggest the host was prepared to avoid detection. |
| Confidence | medium: Both are accurate findings; their link is that they co-occur, not that one caused the other. |
| Enabled by default | yes |
| Needs coverage | `module:persistence` |

**Why it matters.** Attackers who establish persistence commonly also reduce what is recorded. Co-occurrence prioritises this host for investigation over hosts with only one of the signals.

**Conditions.**

- `impair` on `findings`: Logging or protection impaired  
  `check_id in ['CFG-LOG-001', 'CFG-LOG-003', 'EVT-SVC-001', 'EVT-CHAN-001', 'SEC-DEF-001']`
- `persist` on `findings`: A high-signal persistence indicator  
  `check_id in ['PER-CRON-002', 'PER-SYSTEMD-001', 'PER-LDPRE-001', 'PER-WMI-001', 'PER-IFEO-001', 'AUT-CMD-001', ...]`

Requires: `(impair all persist)`.

**Possible benign causes.**

- Hosts with custom logging pipelines that look impaired to the collector, plus an unrelated admin script flagged as persistence.

**Would raise confidence.**

- Timestamps showing the persistence artefact was created after logging was reduced.
- Network activity from the artefact.

**Investigate.**

1. Establish the timeline from file and configuration timestamps.
2. Check whether other hosts show the same pair.
3. Collect volatile evidence \(processes, connections\) before changing anything.

**Remediation.** Restore logging and protection, preserve and then remove the persistence artefact, and review the host for further changes.

**References.**

- ATT&CK [T1562](https://attack.mitre.org/techniques/T1562/) (possible): Impairing defences is a tactic used alongside persistence; co-occurrence here does not prove it.
- NIST SP 800-53 Rev. 5: AU-9, SI-4, SI-7

**Examples (executed by `rules test`).**

- `match`: log redirect plus cron backdoor
- `no_match`: persistence only
- `no_match`: impairment only
- `match`: windows event log service off plus WMI consumer

### DR-ANY-NET-001 - Cleartext remote-access service listening on a non-loopback address

A telnet, FTP, TFTP or r-service port is listening on an address other than loopback.

| | |
|---|---|
| Version | 1.0.0 (pack `correlation`) |
| Platforms | any |
| Category | network-exposure |
| Nature | indicator |
| Severity | high: These protocols send credentials or data unprotected, and TFTP has no authentication at all. |
| Confidence | medium: The port number identifies the usual service; the process may be something else, and reachability depends on filtering. |
| Enabled by default | yes |
| Needs coverage | `inventory:listeners` |

**Why it matters.** Cleartext remote-access protocols expose credentials to anyone on the path and are frequent entry points; a listener on a routable address makes them reachable.

**Conditions.**

- `lst` on `inventory`: A cleartext-protocol port bound to a non-loopback address  
  `(domain eq 'listeners') all (attrs.port in ['21', '23', '69', '512', '513', '514']) all (not ((attrs.bind regex '^127\\.') any (attrs.bind in ['127.0.0.1', '::1', 'localhost', '[::1]'])))`

Requires: `lst`. Items are grouped by `key`.

| Version | 1.0.0 (pack `linux-core`) |
| Platforms | linux |

  `(domain eq 'config') all (key eq 'config:core:core_pattern') all (attrs.value startswith '|') all (not ((attrs.value startswith '|/usr/lib/systemd/systemd-coredump') any (attrs.value startswith '|/lib/systemd/systemd-coredump') any (attrs.value startswith '|/usr/share/apport/apport') any (attrs.value startswith '|/usr/libexec/abrt-hook-ccpp')))`

Requires: `core`.

**Possible benign causes.**

- Vendor crash-reporting agents \(monitoring suites\) that install their own handler.

2. Find where the setting is persisted \(/etc/sysctl.conf, /etc/sysctl.d\).

**References.**

- ATT&CK [T1546](https://attack.mitre.org/techniques/T1546/) (possible): A crash handler is an event-triggered execution point; this does not map to a more specific technique and no abuse is shown.

| Enabled by default | yes |

**Why it matters.** A $-suffixed name hides an account from net user and some GUIs; a password-not-required flag lets the account authenticate with a blank password if policy allows.

### DR-WIN-CRED-001 - Credential protections weakened alongside weakened endpoint defences

LSA/credential-protection settings are weak and UAC or Microsoft Defender is also weakened.

| | |
|---|---|
| Version | 1.0.0 (pack `windows-core`) |
| Platforms | windows |
| Category | credential-access |
| Nature | correlated |
| Severity | medium: Weak credential protection makes credential theft easier, but no theft is observed; severity rises only when Defender is actually disabled. |
| Confidence | medium: The settings are exact; whether they were weakened deliberately is not known. |
| Enabled by default | yes |
| Needs coverage | `module:security` |

**Why it matters.** Credential-dumping tools need weak LSA protection and little interference from endpoint protection. Seeing both together is a preparation pattern, though it also matches poorly hardened hosts.

**Conditions.**

- `lsa` on `findings`: A weak LSA or credential-protection setting  
  `(check_id eq 'SEC-LSA-001') all (evidence.excerpts regex '(?i)(WDigest|RunAsPPL|LM hashes|LmCompatibility|blank-password|anonymous)')`
- `posture` on `findings`: UAC weakened or Defender disabled / broadly excluded  
  `check_id in ['SEC-UAC-001', 'SEC-DEF-001', 'SEC-DEF-002']`
- `defender` on `findings` (optional): Defender protection disabled  
  `check_id eq 'SEC-DEF-001'`

Requires: `(lsa all posture)`.
Severity becomes **high** when `defender`: Microsoft Defender protection is disabled, removing the main control against credential-dumping tools.

**Possible benign causes.**

- Legacy compatibility settings kept for old applications \(for example WDigest for old SSO\).

**Would raise confidence.**

- Event log evidence of LSASS access or of Defender tamper events.
- Changes to these settings since the previous snapshot.

**Investigate.**

1. Check when each setting was changed \(registry key last-write times, GPO history\).
2. Review Defender operational logs for disabled or excluded paths.
3. Look for tools in user-writable folders \(see the filesystem findings\).

**Remediation.** Enable RunAsPPL, disable WDigest, restore UAC and Defender defaults, and remove broad exclusions; test for application compatibility first.

**References.**

- ATT&CK [T1003.001](https://attack.mitre.org/techniques/T1003/001/) (possible): Weak LSA protection facilitates LSASS credential dumping; no dumping is observed.
- ATT&CK [T1562.001](https://attack.mitre.org/techniques/T1562/001/) (possible): Disabled or excluded endpoint protection can indicate impairment of defences; it can also be misconfiguration.
- NIST SP 800-53 Rev. 5: CM-6, SI-3

**Examples (executed by `rules test`).**

- `match`: WDigest plus UAC weakened
- `no_match`: LSA weak only
- `no_match`: UAC weak only
- `match`: defender disabled raises severity

### DR-WIN-LOG-001 - Several event-logging and audit weaknesses together

Three or more different logging weaknesses \(Event Log service, disabled channels, audit policy, PowerShell logging, log size\) are present.

| | |
|---|---|
| Version | 1.0.0 (pack `windows-core`) |
| Platforms | windows |
| Category | defense-evasion |
| Nature | correlated |
| Severity | medium: Each weakness reduces visibility; together they leave little to investigate with, but they also describe an unconfigured host as readily as a tampered one. |
| Confidence | medium: The findings are accurate individually; whether they were set deliberately is unknown. |
| Enabled by default | yes |
| Needs coverage | `module:eventlog`, `module:security` |

**Why it matters.** Adversaries reduce logging before acting. Several independent gaps in one area are worth checking together, but the severity stays medium because default Windows installs also show several of them.

**Conditions.**

- `weak` on `findings` (at least 3 distinct `check_id` values): Logging or audit-configuration findings \(at least 3 different checks\)

### DR-WIN-PER-001 - Registry or WMI persistence mechanism commonly used for stealthy execution

A persistence mechanism that normal software rarely uses \(WMI event consumers, IFEO debuggers, AppInit/AppCert DLLs, LSA packages, Winlogon changes, accessibility-binary replacement, ...\) is configured.

| | |
|---|---|
| Version | 1.0.0 (pack `windows-core`) |
| Platforms | windows |
| Category | persistence |
| Nature | indicator |
| Severity | high: These locations are rarely configured by legitimate software and execute code automatically. |
| Confidence | medium: Security and accessibility products occasionally use these hooks; the collector already filters stock Windows values. |
| Enabled by default | yes |
| Needs coverage | `module:persistence` |

**Why it matters.** Run keys are common and noisy; these mechanisms are specifically chosen by adversaries to execute code at logon, boot or process start without appearing in the usual autorun lists.

**Conditions.**

- `per` on `findings`: A high-signal Windows persistence finding  
  `check_id in ['PER-WMI-001', 'PER-IFEO-001', 'PER-SILENT-001', 'PER-APPINIT-001', 'PER-APPCERT-001', 'PER-ACCESS-001', ...]`

Requires: `per`. Items are grouped by `id`.

**Possible benign causes.**

- Endpoint security and application-compatibility tools that register WMI consumers, IFEO entries or AppInit DLLs.

**Would raise confidence.**

- Binary signature, hash reputation and creation time of the referenced file or consumer.
- The same artefact appearing in an earlier snapshot \(then it is long-standing, not new\).

**Investigate.**

1. Open the evidence reference and read the configured command or DLL.
2. Verify the signature and compare the hash with a trusted source.
3. Establish when it was added \(registry last-write, WMI repository, event logs\) and by which account.

- ATT&CK [T1546.012](https://attack.mitre.org/techniques/T1546/012/) (possible): Image File Execution Options injection is covered by PER-IFEO-001.
- ATT&CK [T1547.004](https://attack.mitre.org/techniques/T1547/004/) (possible): Winlogon helper changes are covered by AUT-WINLOGON-001.

**Examples (executed by `rules test`).**

### DR-WIN-SVC-001 - Privileged service runs a binary from a user-writable path

A service that runs as LocalSystem \(or another built-in privileged account\) has its executable under Users, ProgramData or Temp.

| | |
|---|---|
| Version | 1.0.0 (pack `windows-core`) |
| Platforms | windows |
| Category | services |
| Nature | indicator |
| Severity | high: Anyone who can write the binary or its folder gains SYSTEM privileges when the service starts. |
| Confidence | medium: Some software legitimately installs services under ProgramData, and the data does not show the folder's permissions. |
| Enabled by default | yes |
| Needs coverage | `inventory:services` |

**Why it matters.** A SYSTEM service whose binary lives where standard users can write is a ready-made privilege escalation and a common persistence location.

**Conditions.**

- `svc` on `inventory`: A privileged service with an image path in a user-writable folder  
  `(domain eq 'services') all (attrs.account in ['LocalSystem', 'NT AUTHORITY\\SYSTEM', 'SYSTEM', 'NT AUTHORITY\\LocalService', 'NT AUTHORITY\\NetworkService']) all (attrs.image_path regex '(?i)^\\"?[a-z]:\\\\(users\\\\|programdata\\\\|windows\\\\temp\\\\|temp\\\\|perflogs\\\\|\\$recycle\\.bin\\\\)')`

Requires: `svc`. Items are grouped by `key`.

**Possible benign causes.**

- Per-machine installers that place agent services under ProgramData.

**Would raise confidence.**

- ACLs on the binary and its directory showing write access for non-administrators.
- Missing or invalid Authenticode signature on the binary.

**Investigate.**

1. Check the signature and hash of the binary and its folder ACLs.
2. Find out when the service was created \(event 7045\) and by whom.
3. Look for sibling services or tasks pointing at the same folder.

**Remediation.** Move the binary to a protected location or reinstall the product; remove the service if unauthorised \(disable first\).

**References.**

- ATT&CK [T1543.003](https://attack.mitre.org/techniques/T1543/003/) (possible): Services are a common Windows persistence mechanism; this shows exposure, not creation by an adversary.
- NIST SP 800-53 Rev. 5: CM-7, AC-6

**Examples (executed by `rules test`).**

- `match`: service in ProgramData as LocalSystem
- `no_match`: service in System32
- `no_match`: user-writable path but ordinary user account
- `match`: quoted path in Temp

### DR-WIN-TSK-001 - Privileged scheduled task runs from a user-writable path

| | |
|---|---|
| Version | 1.0.0 (pack `windows-core`) |
| Platforms | windows |

| Confidence | medium: Update agents sometimes keep helpers in ProgramData; folder permissions are not part of the data. |
| Enabled by default | yes |
| Needs coverage | `inventory:scheduled_tasks` |

**Why it matters.** Scheduled tasks start at boot or logon with the task's privileges; pointing one at a writable folder is a standard Windows persistence pattern.

**Conditions.**
