# Security model

## Scope and authorization

BlueOps is for defenders operating on systems they own or are explicitly authorized to administer (competition hosts, owned infrastructure, authorized incident response). It contains no offensive functionality.

## Trust assumptions

- The operator is trusted; the host may be **compromised**. Output from a compromised host (command results, file contents, logs) is attacker-influenced: parse defensively, never `eval`, and treat absent findings as "not detected", not "clean".
- Native binaries on a compromised host may be tampered with. Where feasible, document which checks rely on potentially untrusted binaries and note it in report `errors[]`/descriptions.
- The BlueOps files themselves are trusted only after checksum verification.

## Guarantees (design goals)

| Area | Guarantee |
|---|---|
| Default behavior | Read-only; only the run output directory is written |
| State changes | Require confirmation (or `--yes`), support dry-run, record rollback data first |
| Availability | Protected services/ports from profiles are checked before changes |
| Network | No runtime network access; no remote code execution |
| Evidence | Originals untouched; `manifest.json` with SHA-256 of every output file and collector script (run directories only; verify with `python -m shared.reporting.verify`); UTC timestamps; owner-only permissions; a run directory is never reused |
| Secrets | Never printed/logged/committed; never passed as CLI arguments; command lines are redacted for the forms listed under *Residual risks* |
| Test hooks | Fixture hooks (`BO_ROOT`, `BO_FORCE_MISSING_TOOLS`, `BO_FIXTURE_DIR`, `BO_FORCE_MISSING`) work only with `BO_TEST_MODE=1`; otherwise they are ignored and recorded (`TEST_HOOKS_IGNORED`, exit 6); reports made with them say `host.test_mode` |
| Tool resolution | Linux: `PATH` reduced to system directories plus root-owned, non-writable entries (`PATH_SANITIZED` records what was dropped). Windows: native tools run from `System32` by full path, never through `PATH` |
| Input handling | Reports, diffs, allowlists, configs and manifests are read with one strict loader: size cap, valid UTF-8, no duplicate keys, no `NaN`/infinity, nesting handled; malformed input is exit 3, never a traceback |

## Baseline comparison

`shared.reporting.diff` is offline and read-only: it reads two reports (and an optional config), writes only its result (stdout, or a new file with mode 0600 that is never overwritten), and uses no network. Reports are treated as attacker-influenced input: size and nesting limits, duplicate JSON keys rejected, control characters escaped in text output. Inventories contain no secrets: password state is recorded as `set`/`locked`/`empty`, SSH keys by fingerprint, sensitive command lines and registry data are redacted. `shared.reporting.detect` has the same properties (it only adds rules over the diff, takes the same untrusted input, and validates a supplied `--from-diff` document before use); its text output escapes control characters so a report cannot forge detections, and a rule that fails is reported as incomplete coverage, never as a clean result. A clean diff is not proof of integrity, because a compromised host can alter what its own audit sees; baselines should be taken early and stored off-host.

## Assessment engine

`python -m shared.engine` orchestrates collectors; it never inspects the host itself. It starts programs only as argv lists (no shell), with no stdin, in their own process group so a timeout kills the tree, and only the programs named by built-in modules or by plugin manifests the operator pointed it at. Module reports are untrusted input: strict JSON, schema validation before use, control-character stripping and length caps on every ingested string, and every output format escapes for its medium (the HTML report carries a Content-Security-Policy pinned to its single script). Output directories are created `0700`, files `0600`, exclusively, and never reused; the assessment `manifest.json` lists the SHA-256 of every file (module outputs unchanged), and `verify` refuses unsafe paths and symlinks. **Plugins are the trust boundary:** a plugin is a program you chose to run with the engine's privileges; the engine cannot make it read-only. On POSIX a plugin directory or manifest that group/other can write is refused; on Windows ACLs are not inspected. Modules (and `telemetry collect`) are started with an **allowlisted environment**, not a copy of the caller's (`shared/engine/environment.py`): locale/terminal/identity variables, `LC_*`, `BLUEOPS_*` and `BO_*` pass; `BASH_ENV`, `ENV`, `LD_*`/`DYLD_*`, `PYTHON*` and everything else (including secrets) do not, and the names of withheld loader/interpreter hooks are reported on stderr (never their values), because a planted `BASH_ENV` runs before the first line of a collector and no collector can defend against it. `PATH` is rebuilt as in `linux/lib/common.sh` (system directories, then only root-owned, non-group/other-writable entries; kept as given when `BO_TEST_MODE=1`), and `pwsh`/`powershell` and non-absolute plugin commands are resolved through it. The `BO_*` pass-through includes the collectors' test hooks, which the collectors ignore unless `BO_TEST_MODE=1` and report when used. The Windows rule is only a small denylist of .NET injection variables and **has not been exercised on a Windows host**. The engine itself runs in the environment it was given (`PYTHON*` variables affect the engine's own interpreter), and the `blueops` launcher is a Bash script that cannot protect itself from a `BASH_ENV` set before it starts.

Plugin files are trusted only when, for the manifest, the plugin directory and every file inside it that the command line launches (the program, and a script given to an interpreter), the path is not a symbolic link, is owned by root or the user running the engine, is not group/other-writable, and no ancestor directory is group/other-writable (except sticky ones such as `/tmp`). The files are checked on discovery and again immediately before each launch (`shared/engine/trust.py`). That narrows, but does not close, the gap between check and exec, and ACLs are not inspected. A snapshot comparison never concludes "resolved" or "new" from a module that failed, timed out or was not run.

## Detection engine

Rules are JSON data: loading a rule pack cannot run code, and the engine never reads a host. Rule packs, assessments, history snapshots and the case file are all treated as untrusted input: strict JSON (size caps, duplicate keys, `NaN`, nesting), schema validation, condition and regex limits (length caps, nested quantifiers rejected, inputs capped), bounded work per rule, and a rule that raises is recorded as an error without stopping the others. A rule pack is still *policy*: a malicious or sloppy pack can hide a problem (disabled rule, always-false condition) or flood a report; load packs only from sources you trust and review `rules validate --examples`. Output escaping follows the report rules (HTML escaped and CSP-pinned; Markdown escaped; CSV formula-neutralised). Investigation state is written owner-only under a lock as an append-only, hash-chained JSON-lines file (tamper-evident for earlier lines, not tamper-proof; keep copies off-host) and holds no evidence content. Detections are leads: each carries its `nature` and a disclaimer, and none claims proof of malicious activity.

## Telemetry and hunting

Collectors are read-only, have no network code, and write only to stdout/stderr; the Linux collector reads account databases but never password hashes or private keys (only a locked/set/empty classification), redacts command lines and registry values, and records `authorized_keys` as counts. Telemetry can still contain sensitive data (user names, command lines, source addresses): `telemetry import`/`collect` create stores `0700`/`0600` with a SHA-256 manifest, and raw inputs are kept byte for byte under `sources/`. A stream is untrusted input from a possibly compromised host: records are rebuilt, attribute names and sizes are bounded, timestamps without a zone are refused, event XML is parsed without external entities, queries and rules are data (no code evaluation, nested-quantifier regexes rejected), and reports escape for their format. **A compromised host can lie to its own collector** (rootkits, `ld.so.preload`, forged logs): telemetry from a host is evidence of what it reported, not of what happened; hunting rules therefore say "suspicious" or "unusual", never "confirmed". Nothing is transmitted anywhere; collection is local and explicitly started.

## Input integrity and provenance

**What is required.** Every input that carries data into an assessment, comparison, detection or telemetry result is verified before it is used: a directory must contain a `manifest.json` that matches every file in it, and a collector run directory a valid run manifest. A missing, malformed or non-matching manifest, an unlisted file or a symbolic link is an error (exit 3). `assessment.json` or `report.json` given as a file is verified through its directory. Any other bare file, including a stored comparison passed to `--compare`, has no manifest and is refused. In a `--history` directory a snapshot that cannot be verified is skipped and listed in the run's notes, not read. Telemetry *stores* are verified the same way and have no opt-out.

**Three outcomes, not two.** *Verified*: a manifest exists and every file matched. *Unverified*: there is nothing to verify against (no `manifest.json`, or a bare file) and you explicitly accepted that. *Invalid*: a manifest exists and verification was attempted and **failed** (a file differs, a file is missing or not listed, the manifest is malformed, is of the wrong kind, is a symbolic link or does not match an expected digest, or a listed file is a symlink). Invalid data is refused under every option, including `--allow-unverified`, and a bare file addressed directly in a directory whose manifest fails is invalid too.

**`--allow-unverified` (library: `verify=False`) does exactly this, and nothing more.** It is accepted by every command that reads an input which can lack a manifest: `engine compare`, `engine report`, `engine run` (its `--compare` and `--history` inputs), `detect run`, `detect compare`, `detect report`, `detect show`, `detect export`, `telemetry import`, `telemetry show`, `telemetry query`, `telemetry tree`, `telemetry compare`, `telemetry report` and `telemetry hunt`. **One policy applies to all of them:** a *verified* input is accepted; an *unverified* input (a raw collector stream, a bare `telemetry.json` or detection-results file, a bare report, a directory without a manifest, a stored comparison) is refused (exit 3) unless `--allow-unverified` is given, and is then accepted and recorded as unverified; an *invalid* input is refused always. A lone file inside a directory whose manifest matches is verified by that manifest. Telemetry **stores** (directories written by `telemetry import`) always carry a manifest and have no opt-out at all. The one input that is trusted without a manifest is the stream `telemetry collect` captured in the same process (it is recorded as `(this run)`). Only the *unverified* case is accepted: an input with no manifest to check, or a bare file, is loaded and recorded as **unverified**, with the reason; an input that verifies is recorded as verified. An *invalid* input is refused (exit 3; in a `--history` directory it is skipped and listed in the notes; in `run --compare` it is reported as `comparison skipped` and the run exits 6). Malformed or schema-invalid data and symbolic links are refused too, the flag never applies to modules, plugin trust or the environment, and it cannot be combined with an expected manifest digest. Use it only for data you already trust, such as synthetic fixtures.

**Provenance is recorded in every derived output.** Assessments, snapshot comparisons, detection results, detection comparisons, telemetry documents and telemetry comparisons carry `inputs` (one entry per input: `role`, `path`, `verified`, and a `reason` when not verified) and `inputs_verified`, which is true only if every entry is. Per-input entries are authoritative; the boolean is only the summary. An input that was itself derived from unverified inputs keeps those entries (`via` names the carrier), so a clean manifest on a later file does not launder what it was built from. An input whose provenance is unknown (a document rebuilt or copied without its record) counts as unverified; schema validity never makes anything verified. Markdown, HTML and text reports show a warning at the top when any input is unverified and list every input with its status; JSON Lines and CSV detection exports repeat the status on every row. A document with no provenance record (written by an earlier version) is shown without a claim either way.

**Stored outputs and legacy tools.** A saved detection-results file read by `detect show|export|report` or `telemetry report --detections` is verified through its directory's manifest when it has one (a failing manifest is invalid, whatever the flag says); with no manifest it is refused unless `--allow-unverified`, and is then recorded as unverified. A provenance claim written inside such a file never makes it verified. **Case store:** `--state-dir` registers detections as cases, and each observation records whether the results it came from were `verified`, `unverified` or `unknown` (no provenance record, counted as unverified). A case is shown as verified only if *every* observation of it was; one unverified or unknown source makes it unverified for good, and a later verified observation does not undo that. Invalid data never reaches the store. **Legacy tools:** the `blueops-diff` / `blueops-detect` outputs (`baseline-diff`, `detections`, schema 0.2.0) keep their documented, input-form-independent format and so carry **no** provenance fields. Their loader verifies a run directory that has a manifest (a failing or symlinked manifest is refused), and for any input it could not verify (a bare report, a directory without a manifest, a saved `--from-diff`) it now prints an `UNVERIFIED` warning per input on **stderr**, which `--quiet` does not hide; stdout and `--output` files are unchanged. A pipeline that reads only stdout, or discards stderr, still sees no marker: for verified provenance use the engine commands.

**Limits of a self-contained manifest.** The manifest sits next to the data it describes. It detects accidental corruption and changes that did not also rewrite the manifest; it does not stop someone who can write the directory from changing the data *and* the manifest. To close that gap, record the manifest's SHA-256 off the host when the run finishes and check it later with `engine verify DIR --expect-sha256 DIGEST` (library: `load_assessment(..., expected_sha256=...)`); the comparison, report, run and detection commands do not take a digest. `inputs_verified: true` therefore means "the files still match the manifest they came with", not "the data is true" or "the author is known".

**Residual time-of-check/time-of-use risk.** Verification hashes the files, then the loader reads `assessment.json` again; a process that can write the directory between the two can substitute data that was not hashed. Keep input directories owner-only (the tool creates them `0700`/`0600`), do not verify data in a directory other users can write, and copy untrusted data to a private location before loading it.

## Runtime environment and plugin trust

**Environment sanitization.** Modules and `telemetry collect` are started with an allowlisted environment, not a copy of the caller's (`shared/engine/environment.py`): locale, terminal and identity variables (`HOME`, `LANG`, `LANGUAGE`, `TZ`, `TERM`, `TMPDIR`, `USER`, `LOGNAME`, `NO_COLOR`, `LC_*`) and anything named `BLUEOPS_*` or `BO_*` pass; everything else does not, including secrets and the loader and interpreter hooks (`BASH_ENV`, `ENV`, `LD_*`, `DYLD_*`, `PYTHON*`, `PERL5*`, `RUBY*`, `NODE_OPTIONS`). The *names* of withheld hooks are reported on stderr, never their values. `PATH` is rebuilt from the system directories plus only those entries that are root-owned and not group/other-writable, and `pwsh`, `powershell` and non-absolute plugin commands are resolved through it.

**Exceptions and limits.** (1) With `BO_TEST_MODE=1` the given `PATH` is kept as it is; whoever controls the whole invocation can set it, and reports made that way say `test_mode`. (2) `BO_*` passes through, which includes the collectors' test hooks; the collectors ignore them unless `BO_TEST_MODE=1` and report when they were used. (3) The engine process itself, and the `blueops` launcher (a Bash script), run in the environment they were given: a `BASH_ENV` or `PYTHON*` variable set before they start affects them and cannot be defended against from inside. (4) On Windows the rule is a small denylist of .NET host-injection variables (`COR_*`, `CORECLR_*`, `COMPLUS_*`, `DOTNET_STARTUP*`, `DOTNET_ADDITIONAL*`, `__PSLOCKDOWNPOLICY`) and has **not been exercised on a Windows host**; it is not an allowlist.

**Plugin trust (POSIX).** A plugin's manifest, its directory and every file the command line launches (the program, or the script given to an interpreter) must not be symlinks, must be owned by root or by the user running the engine, and must not be group- or other-writable; no ancestor directory may be group/other-writable unless it is sticky (`/tmp`). This is checked when the plugin is discovered and again immediately before each launch; a failure is a `failed` module with the reason. Built-in modules are exempt. **Limits:** only the files named on the command line are checked, so a plugin that imports sibling modules, sources other scripts or reads data files from its directory is not covered for those files; there is a short window between the launch-time check and the program starting; and on Windows ACLs are not inspected, so protect plugin directories yourself. A plugin is a program you chose to run with the engine's privileges, and review is the control that matters.

**Breaking change: plugins no longer inherit the caller's environment.** A plugin sees only the allowlisted variables above. A variable it needs must be passed as `BLUEOPS_<NAME>` (set in the engine's environment), and tools it needs must be in a root-owned system directory or addressed by absolute path; a tool in a user-writable `PATH` directory is no longer found, and credentials or tokens present in the caller's environment are not forwarded. Existing plugins that read an unprefixed variable (`MY_API_URL`, `HTTP_PROXY`, ...) must be changed.

## Residual risks (known, documented, not fixable in the collectors)

* **A root-level attacker can rewrite file and checksum together.** `--package-integrity` trusts the package database on the same host (dpkg's MD5 lists, the rpm database); the run manifest trusts the directory it sits in unless its digest is recorded off-host.
* **A manifest next to its data proves consistency, not authorship** (see *Input integrity and provenance*); only an off-host digest detects a manifest rewritten with the data, and verification is followed by a separate read of the file (TOCTOU).
* **Bare telemetry streams and `telemetry.json` files have no manifest.** They are refused unless `--allow-unverified` is given (the one input policy); once accepted, every output built from them says `inputs_verified: false`.
* **Plugin trust covers launched files, not what they import or read** (see *Runtime environment and plugin trust*).
* **Redaction is pattern-based.** Handled: `name=value` secrets, `--password X`, URL credentials, `Authorization` headers, `curl -u user:pass`, `sshpass -p`, mysql-style `-pSECRET`, and the Windows equivalents. Not detectable: secrets read from stdin or here-strings, in files, or as positional arguments of arbitrary programs. Evidence may therefore still contain sensitive data; its permissions are owner-only.
* **Text is escaped, not decoded.** Non-ASCII bytes appear as `\u00XX` per byte on Linux and `\uXXXX` per UTF-16 unit on Windows, so distinct names stay distinct; a UTF-8 name looks like mojibake in the raw report.
* **`BO_TEST_MODE=1` is an explicit opt-in.** An attacker who controls the audit process environment completely can set it; the report then says `test_mode` and the comparison tools warn (`TEST_MODE`). The gating defeats a stray or planted *hook* variable, not an attacker who owns the whole invocation.
* **The comparison trusts a report's own statements** (coverage, host name). See [baseline-diff.md](baseline-diff.md).
* **Windows signature checks may touch the network.** Authenticode verification is done by Windows and may query revocation endpoints on a connected host; BlueOps does not control it. On an isolated host those lookups time out and are cached.

## Non-goals

Offensive security, exploit development, anti-forensics, or covert operation. Not a replacement for EDR/SIEM.

## Threats considered

Argument/path injection, unsafe temp files and symlink attacks, secret leakage in output, evidence tampering, accidental service disruption, supply-chain compromise (CI actions and dev dependencies are tracked by Dependabot; CI uses least-privilege `contents: read`).

Report vulnerabilities per [SECURITY.md](../SECURITY.md).
